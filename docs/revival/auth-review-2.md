## perf-threading

### [confirmed] [blocker] PT2-01 — `leaf-server/src/main/java/gg/hcfrevival/revival/auth/net/ArrivalStamps.java:73`

**Problem:** `handler` (lines 33-41) is one anonymous `ChannelInboundHandlerAdapter`, not `@Sharable`, created once per AuthPlayer. `install()` adds that same instance on every activation. Netty refuses to add a non-sharable handler again once it has been added and removed. I reproduced this against netty-transport 4.2.17 with an EmbeddedChannel: add, remove, add again throws `ChannelPipelineException: ... is not a @Sharable handler, so can't be added or removed multiple times`. Failure path: an admin runs `/revival auth mode off` then `/revival auth mode enforce`, or `/revival reload` turns `authoritative.mode` off and back on, or a plugin calls `AuthPlayer.setOverride(OFF)` and later re-enables it. On each online player's next TickEnd, `switchMode` → `activate()` → `installAuditor()` → `arrivals.install()` throws before anything else in `activate()` runs. `ServerPacketListener.onPacketError` logs "Failed to handle packet ..., suppressing error" with a stack trace. `mode` stays OFF, so every later TickEnd repeats this. The player never gets authority again this session (no movement, timer or reach authority), and the log gets about 20 stack traces per second per player, around 2000/s at N=100, which costs main-thread time and disk. The live suites can't catch it: FakeClient's EmbeddedChannel has no `packet_handler`, so `install()` returns false there. A smaller race in the same code: `uninstall()` (lines 84-87) calls `pipeline.get(HANDLER)` and then `pipeline.remove(HANDLER)`. If the channel is torn down on the event loop between those two calls, `remove` throws NoSuchElementException out of `deactivate()`.

**Fix:** Make the handler a named static or inner class annotated @ChannelHandler.Sharable. Its only state is the outer ArrivalStamps, already synchronized. Or allocate a new handler on each install(). In uninstall(), call pipeline.remove(handlerInstance) inside try/catch(NoSuchElementException). Add a unit test: an EmbeddedChannel with a 'packet_handler' handler goes install → uninstall → install.

**Evidence:** ArrivalStamps.java:33-41 creates one anonymous ChannelInboundHandlerAdapter per instance, and the instance is one per AuthPlayer (AuthPlayer.java:619, a final field). activate() → installAuditor() → arrivals.install(channel) at AuthPlayer.java:624 is the first statement of activate(). deactivate() → uninstallAuditor() → arrivals.uninstall() removes it. switchMode only calls activate() when mode is OFF (AuthPlayer.java:438), so the second install happens on any OFF→on transition. Those come from /revival auth mode via AuthCommand.java:99/108 → Authority.setModeOverride, from a reload of authoritative.mode, or from AuthPlayer.setOverride. I reproduced it against the cached netty-transport 4.2.17.Final, the version leaf-server/build.gradle.kts:212 pins. An EmbeddedChannel with a 'packet_handler' runs addBefore of the anonymous adapter, then remove, then addBefore again, and the second add throws `ChannelPipelineException: T$1 is not a @Sharable handler, so can't be added or removed multiple times`. The throw happens before `this.mode = wanted` (AuthPlayer.java:444) and before Authority.activated, so mode stays OFF and every later TickEnd (onTickEnd:983-984) repeats it. The exception goes PacketProcessor.ListenerAndPacket.handle → ServerCommonPacketListenerImpl.onPacketError → ServerPacketListener default, which logs "Failed to handle packet {}, suppressing error" with the trace (ServerPacketListener.java:13-14), plus server.reportPacketHandlingException. installedOn is never set because addBefore threw, so uninstall() stays a no-op and nothing self-heals. The live rig can't catch it: FakeClient and RecordingConnection use a bare `new EmbeddedChannel()` with no packet_handler, so install() returns false there. The secondary get-then-remove race in uninstall() (lines 84-87) is also real: pipeline destroy on the event loop between the two calls makes remove(String) throw NoSuchElementException. Its window is tiny.

### [confirmed] [major] PT2-02 — `leaf-server/src/main/java/gg/hcfrevival/revival/auth/Authority.java:404`

**Problem:** ACTIVE is never pruned when a player quits. `activated()` adds the AuthPlayer. `deactivated()` only runs from `deactivate()`, which needs a TickEnd or a window overflow, and no disconnect hook calls it (the patched sources call only intercept, onServerTick, onTeleportSent, onTeleportAccept and skipsTravel). The only pruning is `activePlayers()`'s removeIf. That method is called only by the new TruthPaths, for attacks past the rewind cap, and by `/revival auth`. Failure scenario: a 100-player HCF server where every RTT is under rtt-ceiling-ms, so no attack goes past the cap and nobody runs the command. After 5,000 sessions, the static list strongly holds 5,000 disconnected ServerPlayers, each with its PlayerAdvancements, stats and inventory. It also holds each player's full auth state: Transactions rings and spare or sent bundle lists, MirrorBook histories, the WorldView chunk set and overlays, SolidMirrors, the PathWiring Target with its ring and viewer maps, and the closed Channel through `arrivals.installedOn`. That is on the order of 1 MB per session, so old-gen grows by GBs over days, leading to long GCs and then OOM. Side effects: `activated()`'s `ACTIVE.contains` is a linear scan over every leaked entry on each join, and `onPaired`'s `!ACTIVE.isEmpty()` gate stays open forever. TruthPaths now prunes only by accident, and it allocates an `unmodifiableList` wrapper and runs a removeIf on every call.

**Fix:** Prune on quit: call revivalAuth.deactivate() or Authority.deactivated() from the disconnect path (ServerGamePacketListenerImpl.onDisconnect or PlayerList.remove), or run an ACTIVE.removeIf once per server tick in noteServerTick. Make activePlayers() a non-mutating read. TruthPaths can resolve the target through level.getEntity(id).revivalAuth instead of scanning.

**Evidence:** Authority.java:393-407: activated() adds to the static ACTIVE list, and deactivated() removes from it. deactivated() is called only from AuthPlayer.deactivate() (AuthPlayer.java:766), which runs only from switchMode(OFF) on a TickEnd (line 427) or from windowOverflow (line 3126). A grep of leaf-server/src/minecraft shows no disconnect or PlayerList.remove hook into auth; the only auth hooks are intercept, onServerTick, onTeleportSent/Accept, skipsTravel, and the static Authority hooks. Nothing in gg/hcfrevival listens for quit. The only pruning is activePlayers()'s removeIf(hasDisconnected) (line 405). Its only callers are TruthPaths.positionSince (TruthPaths.java:25), which runs only when an attack's rewind exceeds the cap (HitValidator.java:80-82, NeueReach.java:47-48), and AuthCommand.java:77/85. AuthPlayer.player is a final ServerPlayer, so each leaked entry pins the whole ServerPlayer plus the auth state. The `!ACTIVE.isEmpty()` gates in onBlockChanged (line 175) and onPaired (line 238) stay open, and activated() does a linear contains. One caveat on impact: capped attacks are not rare in real fights. Any attacker above rtt-ceiling-ms (250) or any target stall (see PT2-05) triggers a prune, so the multi-GB-to-OOM outcome needs long stretches with no capped attack. The missing prune on quit is still a real leak.

### [confirmed] [major] PT2-03 — `leaf-server/src/main/java/gg/hcfrevival/revival/auth/PathWiring.java:212`

**Problem:** `drain()` re-pairs every fed target whose mirror is inexact, with only the `mayRepair` interval limiting it. It never checks the viewer's `forcedOutstanding()`. This round added that gate to `repairMirrors`, `repairSolids` and `updatePathStep` because, in the code's own words, "a re-pair while they lag is forced too, and loops". The repair here does exactly that. When a viewer's downlink stalls or saturates, its path steps are forced at the deadline. `MirrorBook.queue` marks every forced event inexact, including the Spawn. So every fed target is re-paired every `repair-interval-ticks` (20), each re-pair is forced, and the mirror stays inexact, round after round, until the acks catch up. Each re-pair costs `removePairing`/`addPairing` on the server thread (AddEntity, full entity data, equipment, attributes, passengers) and roughly 0.5-1 KB downstream to a client whose link is already the bottleneck. In the documented N=100 collapse (forced entries across most viewers, about 50 fed targets each), that comes to thousands of spawn bundles per second on the server thread and on the saturated links. It feeds the very cascade Load P0 was meant to break.

**Fix:** In drain, add `&& !fed.player.revivalAuth.transactions().forcedOutstanding()` to the inexact branch only. Keep RESPAWN ungated. When acks catch up, the forcedSinceCatchUp → repairMirrors pass and the next drain restore exactness with one re-pair.

**Evidence:** PathWiring.drain line 212: `result == RESPAWN || inexact(fed, id) && target.mayRepair(viewer, currentTick, settings)` → removePairing/addPairing. There is no forcedOutstanding() check. The same round gated the other re-pair paths: the repairMirrors call at AuthPlayer.java:1184-1186, the catch-up repair at 1583-1589 (comment: "a re-pair while they lag is forced too, and loops"), repairSolids at 1934 ("the re-pair would be forced too"), and updatePathStep at 1207. repairMirrors also skips fed targets (`PathWiring.feeds(...)` → continue), so drain is the only repair path for in-range targets, and it is the ungated one. Forced entries are applied with exact=false (AuthPlayer.java:1415-1420 → applyGuarded(..., false, ...)) → CombatWiring.onApplied → MirrorBook.onPacket(..., exact=false) sets unbracketed. queue() then enqueues INEXACT after the event, "so a Spawn (which starts exact) is still marked" (MirrorBook.java:354-359). Moves get the same treatment (lines 298-301). So while a viewer's acks lag past the deadline, its fed mirrors go inexact and each fed target is re-paired once per repair-interval-ticks (20). If the lag persists, the re-pair's AddEntity is itself forced, re-marked inexact, and re-paired 20 ticks later.

### [confirmed] [major] PT2-04 — `leaf-server/src/main/java/gg/hcfrevival/revival/auth/PathWiring.java:201`

**Problem:** When a viewer comes into `exact-radius`, `drain()` creates its Fed with `target.feed.viewer()`, which uses the feed's default K (`path-step-ticks`, 2). It ignores the viewer's own `pathStepTicks()`. Only `onPaired` (line 137) applies the per-viewer K1, and only when the pairing happens within 24 blocks. Players pair at the tracking range (48-128 blocks), so in almost every real fight the target reaches 24 blocks through this branch and is fed at K2. The same happens every time a target leaves (past 28 blocks) and comes back, and to every target that wasn't fed at the moment of the K switch. Result: the torture-K1 gain (50 ms less view latency on remote players for low-jitter viewers) is mostly not delivered, and each viewer gets a mix of K1 and K2 targets depending on how they arrived.

**Fix:** At line 201, use `new Fed(target.feed.viewer(viewer.revivalAuth.pathStepTicks(settings)), viewer)`. Add a live check: a K1 viewer has a target walk in from beyond exact-radius, and the check asserts the Fed's stepTicks()==1.

**Evidence:** PathWiring.java:201 builds the Fed with `target.feed.viewer()`. PathFeed.viewer() (PathFeed.java:198-199) returns `new Viewer(this.settings.stepTicks())`, the feed-wide path-step-ticks (default 2, from Target's constructor at PathWiring.java:62-63). Only onPaired (line 137) uses `viewer.revivalAuth.pathStepTicks(settings)`, and it returns early when the pair is beyond exact-radius (line 132, default 24). Player pairing happens at tracking range, beyond 24, so a target that walks into range is fed through the drain branch at K2 whatever the viewer's K1. The same holds after every leave (past 28) and re-entry. updatePathStep's switch (AuthPlayer.java:1236-1244) only re-pairs targets fed at that moment, and nothing later corrects a Fed whose stepTicks disagrees with the viewer's K. So K1 viewers get a mix of K1 and K2 targets.

### [confirmed] [major] PT2-05 — `leaf-server/src/main/java/gg/hcfrevival/revival/auth/replicate/PathFeed.java:144`

**Problem:** This is outside the perf lens, but it is on the new TruthPaths path. `positionSince` returns MIN_VALUE when even the newest step is older than `now − cap`. HitValidator (line 82) and NeueReach (line 48) then return INVALID REWIND. A target under authority appends no steps while it sends no TickEnds (lag switch or upstream stall), while its windows are refused (frozen or timer), and while one of its server teleports is pending (`AuthPlayer.java:2066`, `teleportsPending == 0` gate). In all three cases the attacker's mirror keeps showing the last step, its stamp keeps aging, and once it passes the attacker's cap every melee hit and every Neue landing on that target is INVALID. A lag-switcher is therefore unhittable for the rest of each hold once it lasts longer than the attackers' caps (about 300-550 ms), and stays unhittable while frozen. That contradicts "the frozen player stays where the truth is, hittable" and HitValidator's own doc, which says only targets outside authority are REWIND. A high-ping target is also briefly unhittable after each pearl or teleport, for its RTT. Its truth hasn't moved in that time, so the newest step is the truth at the capped age.

**Fix:** In TruthPaths/PathFeed: when the target is still replicated and no step is at least as new as sinceMillis, return the newest step (no tick ran since, so it is still the truth). While a server teleport is pending, use the simulation or server position. Keep MIN_VALUE only for targets with no feed. Add a cheat-suite row: the target withholds TickEnds for 1 s while the attacker swings at the frozen box, and every hit must be VALID.

**Evidence:** PathFeed.positionSince (lines 133-151) walks newest-first and breaks at the first stamp < sinceMillis. If the newest step is already older, found stays -1 and it returns Long.MIN_VALUE. Steps are appended only from runWindow: the pathSink().onTick calls at AuthPlayer.java:2066-2068 under `teleportsPending == 0`, and at 2095-2096, which skips EXEMPT_REFUSED / NOT_LOADED and pending teleports. A target that sends no TickEnd runs no window. Frozen enforce windows are refused (runReadyWindows:1373-1375 → EXEMPT_REFUSED, 'Frozen: no physics'). So no step is appended in any of the three cases. PathFeed.Viewer.drain sends nothing when nothing was appended, keep-alive nudges included (they happen per appended step). The attacker's RemoteMirror stamp therefore stops refreshing; refreshTargetStamp only runs on incoming events. HitValidator.java:78-84: rewind = now - s.stamp > cap → positionSince(now - cap) == MIN_VALUE → INVALID REWIND. NeueReach.java:47-50 returns NaN the same way. AuthPlayer.java:1814-1818 delivers a player hit in enforce only when verdict == VALID. With cap = min(rttBase,250) + display + jitter + 150 slack, a target stalled for more than about 300-550 ms is unhittable. This contradicts the stated intent at AuthPlayer.java:1170-1171 ("The frozen player stays where the truth is, hittable") and pvp-issues.md NW-2 ("stays hittable where it froze"), and HitValidator's own doc, which says only a target outside authority is REWIND.

### [confirmed] [minor] PT2-06 — `leaf-server/src/main/java/gg/hcfrevival/revival/auth/AuthPlayer.java:1230`

**Problem:** Each K switch in `updatePathStep` re-pairs every target currently fed to the viewer: RemoveEntities plus a full spawn bundle per target, built on the server thread, and a reset mirror and pre-roll per target. In a 40-50 player teamfight within 24 blocks, a Wi-Fi viewer whose jitter hovers around the 25/35 ms thresholds can flip about every 10 s (5 one-second checks per side). Each flip costs about 50 spawn bundles (roughly 1 ms of server thread and 30-50 KB of burst) for that viewer, at the moment its link is shaky. Most of that work is wasted anyway, because targets that re-enter range go back to K2 (PT2-04). RemoteMirror already models each step's own tick count (`addStep(..., ticks)`, `queueTicks`), which suggests an in-place K change would stay exact.

**Fix:** Prefer an in-place K change (a setter on PathFeed.Viewer.stepTicks that applies from the next step), checking with the mirror suite that RemoteMirror's per-step ticks keep it exact. Otherwise spread the re-pairs: one target per tick, or lazily at each target's next natural re-pair or re-entry.

**Evidence:** AuthPlayer.updatePathStep (lines 1205-1245): on a switch it loops over level.players(), and for every target fed to this viewer (PathWiring.feeds) it calls tracked.serverEntity.removePairing + addPairing on the main thread. Each one is a full spawn bundle plus a fresh mirror and pre-roll. The comment confirms the design ("a switch re-pairs every player fed to this viewer, whose feed then starts over at the new K"). The flip-rate estimate is an upper bound and is overstated. rttHigh/rttBase are p90/p10 over the last 256 acks (Transactions.java:969-971, about 12.8 s of acks). K1 also needs ackedCount >= 256, and a switch needs 5 consecutive one-second checks past the 25/35 ms hysteresis (step-switch-seconds 5), so a switch every ~10 s needs the smoothed jitter to swing across both thresholds that fast, which is rare. The per-switch burst is still real. The 'wasted' point holds because of PT2-04: targets that come back into range return at K2.

### [confirmed] [minor] PT2-07 — `leaf-server/src/main/java/gg/hcfrevival/revival/auth/combat/SolidMirrors.java:579`

**Problem:** Per-viewer cost grows quadratically near shulker clusters, and the hot paths allocate. Every client tick of every viewer, `tick()` walks all held solids twice (before and after the player). Each shulker whose lid is moving allocates in `shulkerBox()` (line 704: `new Vec3` plus `getProgressAabb`'s AABB) and in `getProgressDeltaAabb` (line 579). Each opening lid then scans `all` again for boats in its slab (lines 580-585), which is O(S²) per viewer per tick. `remove()` uses `ArrayList.remove(Object)` (line 312), which is O(S) per id. `ExternalMovers.near` calls `anyUntrusted()` and `untrustedWithin()` every tick (two O(S) scans, lines 828-850), and while any copy is untrusted, which is permanent for a copy whose repair was skipped, it also calls server `getEntities`. Scenario: an End city or shulker farm with 100 shulkers within the 96-block tracking range of 20 viewers, about 20 % peeking. That is roughly 20 × 20 × 100 = 40k box tests plus about 2k Vec3/AABB allocations per server tick, before any collision gathers, and `collect()` walks all S on every collide the port issues. Each opening lid also breaks and re-pairs any boat in its slab, so a boat parked next to a shulker is re-spawned to every viewer on every peek cycle.

**Fix:** Compute shulker boxes inline into the Solid's fields, with no Vec3/AABB, and test the slab with primitives. Skip the slab scan when no non-shulker solid is held, or index boats and ghasts separately. Swap-remove using an index stored on Solid. Keep an untrusted counter maintained by broke/markUnknown/passengers/add/remove so anyUntrusted() is O(1). Rate-limit lid-caused repairs per entity.

**Evidence:** SolidMirrors.tick (lines 483-513) walks `all` on every call, and AuthPlayer.tickSolids (line 1919) runs it per client tick, once with beforePlayer and once without, so all S is visited twice. shulkerTick, while the peek moves, calls shulkerBox (line 704: `new Vec3(...)` plus Shulker.getProgressAabb's AABB) and, when opening, Shulker.getProgressDeltaAabb(..., new Vec3(...)) (line 579). It then rescans all S for non-shulker solids in the slab (lines 580-585), which is O(opening × S) per viewer tick. `all` is a java.util.ArrayList, and remove(int) does all.remove(s) (lines 162, 309-313), O(S). ExternalMovers.near (lines 79-95) calls anyUntrusted() (an O(S) scan) and, when it is true, untrustedWithin() (O(S)) plus level.getEntities. anyUntrusted is true for any copy that is inexact, unknown, a passenger or driven, so one ridden boat in range keeps it true. A boat in an opening slab is broke() → queued repair → re-paired, and repairQueued is reset only by a fresh spawn, so this repeats every peek cycle. Caveat: the absolute cost in the scenario (~40k box tests and ~2k short-lived allocations per tick across 20 viewers) is small, likely well under a millisecond with TLAB and escape analysis. The 100-shulker cluster within tracking range of 20 fighting viewers is niche on HCF. Minor severity fits.

Mirror the change in NeueReach.authority, flip HitValidatorTest.pastTheCapWithNoTruthThatNewItIsRewind for the stopped-path case, and add live rows: 'hit a target frozen for 3 s' and 'stall 1 s, burst 20'.

### [confirmed] [blocker] X2-02 — `leaf-server/src/main/java/gg/hcfrevival/revival/auth/net/Transactions.java:563`

**Problem:** The new ping stamps (F3) let a client void its ack deadlines for as long as it stalled. windowTick() and pacedTick() extrapolate by wall time since the last TickEnd (AuthPlayer.java:351-368), and the stamps only ratchet up (Transactions.java:563-566, stampsNeverGoBack). After a stall of S seconds, every ping is stamped about W + S/50. The timer then lets the client run only about 22 windows at once and real time after that, so its window and paced counts stay below that stamp for about S seconds. forceDue (858, called at AuthPlayer.java:1415) forces nothing in that time, and the only bound on holding a pong is max-unacked-ms (1.5 s, the freeze). Scenario: cheater C stalls for 20 s, sending only keep-alives (and it is immune meanwhile per X2-01). It resumes and fights. On each knock it withholds the pong of that ping and all later ones for about 1.4 s while ticking normally. The truth runs about 28 windows without the knock, and the knock lands in the window C chooses. That is roughly a 1.4 s velocity delay, against 5 windows in cheat-suite row 21. The same delay applies to every logged world change. C's truth, and the ServerPlayer through the uncollided truth write, walks through a block, cobweb or boat dropped in its path. Even without a stall, C can send TickEnds in bursts of 11 (one paced, ten within catch-up-gap-ms and with no pong). The paced count then barely moves, and the knock waits for the any-window cap of deadline + max-banked-ticks: 15 windows instead of 5.

**Fix:** Cap the extrapolation at what the client can catch up: stamp = min(windowTick + ticksSinceArrival, lastClosedWindow + 1 + maxBankedTicks), and the same for paced. Never carry a stall's deficit forward in the ratchet, for example by clamping lastWindowStamp the same way. Add a wall-clock backstop in forceDue that forces any ping older than slackRtt + (ack-jitter-ticks + max-banked-ticks) x period, whatever the window counts say. Add cheat rows: 'stall 10 s, then delay knock pongs 20 ticks' and 'bunch TickEnds by 11 while holding a knock pong'.

**Evidence:** AuthPlayer.windowTick()/pacedTick() (350-358) add ticksSinceArrival(), which is (now - windowArrivalNanos)/period - 1 and is unbounded (361-368). Transactions.newPing (563-566) ratchets lastWindowStamp/lastPacedStamp with Math.max. These stamps reset only in reset() (993-994), which runs only on activation or deactivation (AuthPlayer 707, 779), not after a stall or a freeze. After an S-second stall every ping is stamped about W + S/50. Resumed windows get windowTick = stream.currentTick() (W+1, W+2, ...), so later pings keep the ratcheted stamp until the real window count reaches it, about S seconds minus the catch-up burst.

forceDue (850-871) forces a ping only when pacedWindow - pingPaced >= deadline OR window - pingWindows >= deadline + maxBanked. Both are negative during that time, so nothing is forced. The only remaining bound on a held pong is updateFrozen at max-unacked-ms (1500), which freezes and never kicks. A 20 s stall is about 400 heartbeat pings, far below MAX_PINGS (16384), so no overflow resync clears the ratchet. Unacked knocks reach the truth only at their pong (inFlightKnocks doc: 'the truth takes them at that pong'), so the client picks the window.

I also checked the burst variant. ClientStream.close (492-498) marks at most maxCatchUp (10) consecutive pong-less windows within catch-up-gap-ms as unpaced. A pattern of 1 paced plus 10 catch-up windows advances the paced count once per 11 windows, so only the any-window cap applies: deadline (ceil(rtt/50) + 4 = 5 at 40 ms) + max-banked-ticks 10 = 15 windows. That is the bound the F3 comment documents, but it is three times the intended deadline. I confirmed TickClock with bank plus owed lets 11 run per 550 ms.
